## Текущее состояние и что дальше

Проект строится поэтапно, этап за этапом. На сегодняшний день реализовано:

- **Базовый каркас приложения**: подключение UI-кита Mantine, система работы с серверными данными (TanStack Query), обработка ошибок на уровне страниц, инфраструктура для клиентского состояния (Redux, пока без единого реального раздела состояния), тестовая инфраструктура (модульные и сквозные тесты).
- **Система входа в личный кабинет**: пользователь может авторизоваться (сам процесс входа реализован на уровне сервера), связка с backend через защищённые запросы настроена и работает.

Ещё не реализовано (то есть в коде этого пока нет, но появится по мере разработки):

- Формы входа и регистрации (сама HTML-форма, с которой взаимодействует пользователь).
- Автоматическая защита разделов личного кабинета от неавторизованного доступа (файл `middleware.ts`, который должен это делать, ещё не создан).
- Бизнес-сущности проекта: пользователь, регионы, тарифы, ученик и другие — папка `src/entities/` пока пуста.
- Личные кабинеты Спонсора и Студента, страницы квизов, заданий, копилки и все остальные разделы, кроме главной страницы.

Пока backend, к которому обращается это приложение, — это тестовый сервер уже существующей старой версии проекта (см. раздел [«Прокси к backend»](#прокси-к-backend)), а не отдельно разрабатываемый новый сервер. Это временное решение на период разработки — когда новый сервер будет готов, точка подключения поменяется, но большая часть кода фронтенда трогать не придётся: весь код, который обращается к серверу, сделан так, чтобы адрес backend был вынесен в настройки, а не зашит в код.

## Архитектура проекта

### Идея: Feature-Sliced Design

Весь код в `src/` разложен по пяти слоям. У каждого слоя своя ответственность, и слои образуют строгую иерархию — код из слоя выше по иерархии может использовать код из слоёв ниже, но не наоборот:

```
app  →  widgets  →  features  →  entities  →  shared
```

Слева — самый «верхний» слой (страницы приложения), справа — самый «нижний», универсальный (общий код без привязки к бизнес-логике). Стрелка показывает разрешённое направление использования: `app` может использовать `widgets`, `features`, `entities` и `shared`; а вот `shared` не может использовать вообще ничего из слоёв выше — только другой код внутри `shared`.

Что лежит в каждом слое:

| Слой | Папка | За что отвечает | Статус в проекте сейчас |
|---|---|---|---|
| App | `src/app/` | Маршруты (страницы, URL) и их сборка — не сам код фич, а «монтаж» приложения из остальных слоёв | Есть: корневой layout и одна публичная страница |
| Widgets | `src/widgets/` | Крупные самостоятельные блоки интерфейса, собранные из нескольких фич/сущностей (например, шапка сайта, боковое меню) | Есть: `Header` |
| Features | `src/features/` | Конкретные пользовательские сценарии с действием — «войти», «отправить форму», «купить тариф» | Пока не создано ни одной фичи |
| Entities | `src/entities/` | Бизнес-сущности предметной области — пользователь, ученик, тариф и т.д. Типы данных и запросы за ними | Пока не создано ни одной сущности |
| Shared | `src/shared/` | Переиспользуемый код без знания о бизнес-логике: обёртки над UI-библиотекой, работа с HTTP, конфигурация, утилиты | Есть, наполняется по мере разработки |

Это правило — не просто договорённость. Оно проверяется автоматически при каждом запуске `npm run lint` плагином `eslint-plugin-boundaries` (настройка — файл `eslint.config.mjs`, начиная со строки 54). Если написать в `src/entities/` импорт из `src/features/`, линтер сразу выдаст ошибку и сборка не пройдёт проверку. Специально обходить это правило («ну тут только один раз») не нужно — если тянет так сделать, это обычно сигнал, что код лежит не в том слое.

### Правило «публичного входа» в модуль

Каждый раздел внутри `widgets/`, `features/` или `entities/` (например, будущий `src/entities/user/`) должен экспортировать всё нужное наружу через один файл — `index.ts` в своей корневой папке. Импортировать из кода снаружи модуля можно только через этот `index.ts`, а не по внутренним путям вроде `@entities/user/model/types`.

Пример того, как это уже сделано для `Header`:

```ts
// src/widgets/Header/index.ts
export * from "./header";
```

Использование снаружи:

```ts
// правильно — через публичный index.ts модуля
import { Header } from "@widgets/Header";

// неправильно — так и не сделаешь, линтер запретит:
// import { Header } from "@widgets/Header/header";
```

Смысл: то, что происходит внутри модуля (какие там файлы, как разложен код) — деталь реализации самого модуля. Снаружи важно только то, что он явно решил показать через `index.ts`. Это позволяет менять внутреннее устройство модуля, не трогая код, который им пользуется.

Для `shared/` это правило работает мягче — там достаточно много мелких подпапок (`shared/lib/api`, `shared/api`, `shared/ui/Logo` и т.д.), и у каждой тоже есть свой `index.ts`, но конфигурация линтера (см. `eslint.config.mjs`, правило `boundaries/dependencies`) применяет строгую проверку «только через index.ts» именно к `widgets`, `features` и `entities`.

### Что лежит внутри `shared/`

```
src/shared/
├── api/           — обёртки для запросов, которые выполняются на сервере (Server Components)
├── config/        — настройка сторонних библиотек: тема Mantine, шрифты, next-auth
├── constants/     — общие константы (например, брейкпоинты)
├── lib/           — переиспользуемый код: HTTP-клиенты, TanStack Query, Redux, тестовые утилиты
├── types/         — общие TypeScript-типы и объявления модулей
└── ui/            — переиспользуемые визуальные компоненты (обёртки над Mantine или полностью свои)
```

## Пути импорта (алиасы)

Чтобы не писать длинные относительные пути вида `../../../shared/ui/Logo`, в проекте настроены алиасы — по одному на каждый слой архитектуры. Настройка — `tsconfig.json`, раздел `compilerOptions.paths`:

| Алиас | Соответствует папке |
|---|---|
| `@app/*` | `src/app/*` |
| `@widgets/*` | `src/widgets/*` |
| `@features/*` | `src/features/*` |
| `@entities/*` | `src/entities/*` |
| `@shared/*` | `src/shared/*` |

Пример использования (реальный код, `src/widgets/Header/header.tsx`):

```ts
import { BREAKPOINTS } from "@shared/constants";
import { Logo } from "@shared/ui/Logo";
```

Внутри одного и того же модуля (например, между файлами внутри `src/widgets/Header/`) принято использовать обычные относительные пути (`./header.module.scss`), а не алиас — алиасы нужны именно для переходов между разными частями архитектуры.

Порядок, в котором импорты должны идти в файле (сначала внешние библиотеки, затем алиасы слоёв сверху вниз по иерархии, затем относительные импорты, затем стили), проверяется и автоматически исправляется линтером — правило `simple-import-sort` в `eslint.config.mjs`. Если запутались, в каком порядке расставлять импорты, просто напишите их как угодно и запустите:

```bash
npm run lint:fix
```

## Работа с UI: Mantine и стили

### Mantine — основной UI-кит

Mantine — библиотека готовых компонентов интерфейса (кнопки, поля ввода, модальные окна и т.д.). В проекте её нужно использовать вместо написания своих визуальных компонентов с нуля везде, где Mantine уже предоставляет нужное. Библиотеки Tailwind CSS и shadcn/ui в проекте намеренно не используются.

Настройка Mantine — в `src/shared/config/`:

- `mantine-provider.tsx` — компонент-обёртка `AppMantineProvider`, который подключает Mantine и его тему ко всему приложению. Подключён один раз, в корневом `src/app/layout.tsx`, оборачивать им что-то ещё не нужно.
- `theme.ts` — кастомизация темы: собственная цветовая палитра (`brand`, `orange`, `red`, `textBrand`), размеры шрифтов, скругления. Пример из реального кода:

```ts
// src/shared/config/theme.ts
export const theme = createTheme({
  colors: {brand, orange, red, textBrand},
  primaryColor: 'brand',
  defaultRadius: 8,
  fontFamily,
  // ...
});
```

Если нужен новый оттенок кнопки или другой элемент фирменного стиля — правки вносятся сюда, а не точечными переопределениями стилей в компонентах.

- `fonts.ts` — подключение шрифта Montserrat через `next/font/google` (Next.js сам оптимизирует загрузку шрифта, ничего вручную подключать не нужно).

Использование компонента Mantine в коде — как в обычной React-библиотеке компонентов:

```tsx
import { Button, Title } from "@mantine/core";

export default function Page() {
  return (
    <div>
      <Title order={1}>Заголовок</Title>
      <Button size="sm">Кнопка</Button>
    </div>
  );
}
```

### Собственные визуальные компоненты (`shared/ui`)

Когда нужного компонента в Mantine нет или требуется что-то специфичное для проекта (например, логотип-ссылка на главную), такой компонент создаётся в `src/shared/ui/ИмяКомпонента/` — по образцу уже существующих `ErrorFallback`, `Logo`, `Suspense`. У каждого такого компонента:

- файл самого компонента (например, `logo.tsx`);
- при необходимости — файл стилей рядом (`logo.module.scss`);
- `index.ts`, реэкспортирующий компонент наружу.

### SCSS-модули: когда и как

SCSS-модуль применяется только там, где возможностей темы/пропсов Mantine не хватает — например, для специфичной вёрстки блока (отступы, медиа-запросы для конкретного расположения элементов). SCSS-модуль называется так же, как компонент, с суффиксом `.module.scss`, и лежит в той же папке рядом с файлом компонента.

Пример (`src/widgets/Header/header.module.scss`):

```scss
.header {
  padding-block: 24px;
}

.desktopOnly {
  display: none;
}

.mobileOnly {
  display: block;
}

@media (min-width: 576px) {
  .desktopOnly {
    display: block;
  }

  .mobileOnly {
    display: none;
  }
}
```

Использование в компоненте — импорт как объекта `styles`, обращение к классам через точку:

```tsx
import styles from './header.module.scss';

export const Header = () => (
  <header className={styles.header}>
    {/* ... */}
  </header>
);
```

**Важный пример конвенции проекта**: переключение вида блока между desktop- и mobile-версткой в `Header` сделано через CSS-медиазапрос (файл выше), а не через JavaScript-проверку ширины экрана. Оба варианта верстки всегда присутствуют в разметке, а какой из них видно — решает браузер по CSS-правилу. Это осознанное решение: если переключать версии через JavaScript-хук (например, определять ширину экрана в коде компонента), при первой отрисовке на сервере и в браузере может на мгновение показаться неверный вариант, а сама смена состояния вызывает лишнюю перерисовку компонента. Придерживайтесь этого же подхода, если понадобится похожая ситуация «одно и то же по-разному выглядит на разных экранах».

Если стиль касается не одного компонента, а всего приложения (типографика, общие переменные для контейнеров, глобальные варианты кнопок) — такой SCSS-файл (без `.module.`) кладётся в `src/shared/config/` и подключается один раз в корневом `src/app/layout.tsx`. Так уже сделано с `typography.scss`, `container.scss`, `button-variants.scss`.

Для проверки написания класса `@bem-react/classname` в проекте есть в зависимостях — этот инструмент помогает строить имена классов по методологии БЭМ там, где нужна ручная сборка составных имён классов, отдельно от SCSS-модулей.

## Работа с данными с сервера

Проект использует TanStack Query (`@tanstack/react-query`) для работы с любыми данными, которые приходят с backend. Ключевое правило: **серверные данные никогда не хранятся в Redux** — Redux в этом проекте только для интерфейсного состояния (см. раздел [Redux](#redux-клиентское-состояние-интерфейса)).

### Клиент TanStack Query

Настройка — `src/shared/lib/query/`:

- `query-client.ts` — функция `getQueryClient()`. В браузере она всегда возвращает один и тот же экземпляр клиента (данные кэшируются между переходами по страницам). На сервере — каждый раз создаёт новый экземпляр, потому что один и тот же серверный процесс обслуживает разных пользователей одновременно, и делить между ними кэш нельзя.

```ts
// src/shared/lib/query/query-client.ts
function makeQueryClient() {
  return new QueryClient({
    defaultOptions: {
      queries: {
        staleTime: 60_000,
        retry: 1,
      },
    },
  });
}
```

- `query-provider.tsx` — компонент `QueryProvider`, подключающий этот клиент ко всему дереву компонентов. Уже подключён один раз в корневом `src/app/layout.tsx`, подключать его повторно на страницах не нужно.

### Как выполнять запросы: четыре варианта

В проекте есть четыре способа сходить за данными на backend — выбор зависит от того, где выполняется код (сервер или браузер) и нужна ли авторизация пользователя.

| | Публичные данные (без авторизации) | Данные, требующие входа пользователя |
|---|---|---|
| **Из браузера** (клиентский компонент, `'use client'`) | `$api` — готовый axios-клиент | `$authApi` — готовый axios-клиент |
| **На сервере** (Server Component, без `'use client'`) | `serverFetch<T>(path)` | `authenticatedServerFetch<T>(path)` |

Все четыре в итоге настроены на один и тот же backend — просто разными путями и с разной обработкой авторизации. Подробности того, почему это устроено именно так — в разделах [«Авторизация»](#авторизация) и [«Прокси к backend»](#прокси-к-backend), здесь — как этим пользоваться.

**`$api`** (`src/shared/lib/api/api-client.ts`) — обычный axios-инстанс, для запросов из клиентских компонентов, которым не нужна авторизация пользователя (например, список регионов на странице регистрации):

```ts
import { $api } from '@shared/lib/api';

const response = await $api.get('/regions');
```

**`$authApi`** (`src/shared/lib/api/auth-api-client.ts`) — тот же принцип, но для запросов, которым нужна авторизация. Отличается только `baseURL` — используется точно так же:

```ts
import { $authApi } from '@shared/lib/api';

const response = await $authApi.get('/students');
```

**`serverFetch<T>`** (`src/shared/api/server-fetch.ts`) — обёртка над встроенным в браузер/Node.js `fetch`, для публичных запросов из Server Component (кода, который выполняется на сервере при формировании страницы, до отправки в браузер):

```ts
import { serverFetch } from '@shared/api';

interface Region {
  id: number;
  name: string;
}

const regions = await serverFetch<Region[]>('/regions');
```

При ошибке (backend ответил не 2xx-статусом) `serverFetch` выбрасывает исключение `ApiError`, у которого есть свойство `status` с HTTP-статусом ответа.

**`authenticatedServerFetch<T>`** (`src/shared/api/authenticated-server-fetch.ts`) — то же самое, но для авторизованных запросов из Server Component/Server Action. Если пользователь не авторизован, сразу выбрасывает `ApiError` со статусом `401` — вызывающий код должен сам решить, что в этом случае делать (например, сделать редирект на страницу входа):

```ts
import { authenticatedServerFetch, ApiError } from '@shared/api';

try {
  const students = await authenticatedServerFetch<Student[]>('/students');
} catch (error) {
  if (error instanceof ApiError && error.status === 401) {
    // пользователь не авторизован — обработать соответствующим образом
  }
  throw error;
}
```

### Паттерн prefetch + hydration

Рекомендуемый в проекте способ получать данные для страницы — не ждать запрос в браузере после загрузки, а запросить данные заранее на сервере (`prefetchQuery`) и «передать» уже готовый результат в браузер, откуда клиентский компонент подхватывает его без повторного запроса (`HydrationBoundary`). Так страница показывается пользователю сразу с данными, без лишнего «мигания» состояния загрузки. Использовать этот паттерн стоит для любых данных, которые нужны сразу при открытии страницы.

Готового примера такой страницы в проекте пока нет (появится вместе с первой сущностью в `entities/`), но принцип стандартный для TanStack Query: в Server Component создаётся `QueryClient`, вызывается `prefetchQuery` с нужным запросом, а полученное состояние передаётся в `<HydrationBoundary state={dehydrate(queryClient)}>`, внутри которого уже рендерится клиентский компонент, использующий обычный хук `useQuery` с тем же ключом запроса.

## Авторизация

### Что это за механизм и зачем он такой сложный

Backend, с которым сейчас работает приложение (см. [«Прокси к backend»](#прокси-к-backend)), использует не самый простой способ подтверждения входа — не токен, который можно просто передавать в запросах, а привязанную к домену backend сессионную cookie-запись (такой способ авторизации называется stateful, «сохраняющий состояние на сервере», в отличие от простого токена). Браузер пользователя физически не может напрямую сохранить и использовать такую cookie, потому что она принадлежит другому домену (домену backend, а не домену этого приложения) — так устроены правила безопасности любого браузера.

Поэтому avторизация в проекте построена так: сервер этого Next.js-приложения сам берёт на себя роль посредника между браузером пользователя и backend. Он входит в систему backend от имени пользователя, забирает то, что backend выдаёт при входе, и хранит это у себя — в зашифрованном виде, внутри собственной сессии пользователя (next-auth). Браузер знает только про сессию этого приложения и никогда не видит и не может получить доступ к тому, что происходит между этим приложением и backend. Такой подход, когда сервер приложения выступает посредником-«прослойкой» между интерфейсом и внешним API, в проекте называется просто **посредническим слоем** — весь код для него лежит в `src/shared/api/sanctum-session.ts`, `src/shared/config/auth.ts` и `src/app/api/`.

### Настройка входа (`src/shared/config/auth.ts`)

Здесь настроена библиотека next-auth — определены способы входа (в проекте их два: для Спонсора и для Студента, у каждого свой набор полей для входа) и то, что происходит при успешном входе.

```ts
// src/shared/config/auth.ts (сокращённо)
export const { handlers, auth, signIn, signOut } = NextAuth({
  session: { strategy: 'jwt' },
  providers: [
    Credentials({
      id: 'sponsor',
      credentials: {
        phone: { label: 'Телефон', type: 'text' },
        password: { label: 'Пароль', type: 'password' },
      },
      async authorize(credentials) {
        // ...
        const session = await loginSponsor({ phone, password });
        return {
          id: phone,
          role: SPONSOR_ROLE,
          sanctumCookie: session.cookieHeader,
          sanctumXsrfToken: session.xsrfToken,
        };
      },
    }),
    Credentials({ id: 'student', /* аналогично, по логину и паролю */ }),
  ],
  callbacks: {
    jwt({ token, user }) {
      if (user) {
        token.role = user.role;
        token.sanctumCookie = user.sanctumCookie;
        token.sanctumXsrfToken = user.sanctumXsrfToken;
      }
      return token;
    },
    session({ session, token }) {
      // Намеренно НЕ копируем сюда cookie/токен backend — см. пояснение ниже.
      session.user.role = token.role;
      return session;
    },
  },
});
```

Спонсор входит по номеру телефона и паролю, Студент — по логину и паролю (не по email — это осознанное решение под конкретный backend, к которому сейчас идёт подключение).

**Ключевое правило безопасности этого механизма**: данные для доступа к backend (`sanctumCookie`, `sanctumXsrfToken`) кладутся в зашифрованную сессию (`jwt`-колбэк), но `session`-колбэк — то, что в итоге видит браузер через `useSession()` на клиенте — специально их не копирует. Это значит, что даже теоретически ни один клиентский код не может получить доступ к данным для входа в backend, потому что next-auth физически не отдаёт эти поля в объект сессии, доступный браузеру. Если когда-нибудь понадобится добавить в сессию новое поле — не копируйте в `session`-колбэк ничего, что предполагает работу с backend напрямую, без явного намеренного решения и понимания этого правила.

### Мост к backend (`src/shared/api/sanctum-session.ts`)

Этот файл отвечает за фактическое «общение» с backend на этапе входа: получает специальный защитный токен (CSRF-токен, нужен для защиты от подделки запроса), отправляет логин/пароль, получает и хранит cookie сессии backend. Основные экспортируемые функции:

- `loginSponsor(credentials)` / `loginStudent(credentials)` — выполняют вход, возвращают объект `{ cookieHeader, xsrfToken }`. Используются только внутри `authorize()` в `auth.ts`.
- `logoutSanctumSession(session)` — инвалидирует сессию на backend. Пока никем не вызывается в коде (появится вместе с реализацией кнопки выхода).
- `resolveSanctumSession(req)` — достаёт `sanctumCookie`/`sanctumXsrfToken` текущего пользователя из его сессии. Используется в местах, которым реально нужно сходить за данными в backend от имени пользователя (прокси-обработчик и `authenticatedServerFetch`, см. следующий раздел). Эта функция — единственная точка, где такие данные извлекаются из сессии, поэтому если нужно что-то поменять в этой логике, менять нужно только здесь.

### Как добавить новый защищённый запрос к backend

Если вы пишете код, которому для похода в backend нужна авторизация пользователя:

- **из клиентского компонента** — используйте `$authApi` (см. раздел [«Работа с данными с сервера»](#работа-с-данными-с-сервера)), ничего дополнительно настраивать не нужно, авторизация подставляется автоматически на сервере;
- **из Server Component/Server Action** — используйте `authenticatedServerFetch<T>`, по тем же причинам.

Самостоятельно вызывать `resolveSanctumSession` или работать с cookie backend напрямую в новом коде не нужно — это уже сделано один раз в прокси-слое, о котором дальше.

## Прокси к backend

В проекте есть два независимых способа, которыми запросы браузера или сервера доходят до backend. Различать их важно, чтобы понимать, какой из них трогать при изменениях.

### 1. Публичный прокси (`next.config.ts`, `rewrites()`)

```ts
// next.config.ts
async rewrites() {
  return [
    {
      source: '/api/proxy/:path*',
      destination: `${process.env.API_URL}/:path*`,
    },
  ];
},
```

Это встроенный в Next.js механизм — любой запрос из браузера на путь `/api/proxy/...` автоматически перенаправляется на реальный адрес backend (`API_URL`), но уже с сервера этого приложения, а не напрямую из браузера. Так решается техническое ограничение браузеров (правила CORS — сайт не может напрямую ходить в API на чужом домене без специальной настройки на стороне того домена). Никакой авторизации здесь нет — этот путь использует клиент `$api`.

### 2. Авторизованный прокси (`src/app/api/backend/[...path]/route.ts`)

Отдельный, написанный вручную обработчик маршрута. Через него проходят все запросы клиента `$authApi`. В отличие от первого варианта, этот обработчик:

- проверяет, что пользователь авторизован (через `resolveSanctumSession`, см. предыдущий раздел) — если нет, сразу отвечает статусом `401`, до backend запрос не идёт;
- сам подставляет cookie сессии backend и защитный токен в заголовки запроса к backend — браузер их никогда не отправляет и не видит;
- никогда не пересылает обратно в браузер заголовок `Set-Cookie`, который вернул backend — cookie backend не должна покидать сервер этого приложения ни при каких условиях;
- защищается от попытки выйти за пределы разрешённого пути через `.`/`..` в адресе;
- если backend недоступен — отвечает статусом `502`.

Простого `rewrites()` для этого случая недостаточно именно потому, что подстановку cookie нужно делать динамически, для каждого запроса заново, на основе того, кто именно сейчас авторизован — а `rewrites()` такого не умеет, он просто перенаправляет запрос как есть.

### Когда какой использовать

Не выбирайте это вручную в новом коде — выбор уже зафиксирован тем, каким клиентом вы пользуетесь. Если нужен запрос без авторизации — берёте `$api`/`serverFetch`, и он автоматически пойдёт через публичный прокси. Если нужна авторизация — `$authApi`/`authenticatedServerFetch`, и он пойдёт через авторизованный прокси. Оба обработчика уже написаны и трогать их для того, чтобы добавить новый эндпоинт, не нужно — прокси универсален по пути (`/api/backend/что-угодно` дойдёт до `что-угодно` на backend).

## Redux: клиентское состояние интерфейса

Redux Toolkit в проекте используется **только для состояния интерфейса**, которое не пришло с сервера — например, открыта ли модалка, на каком шаге многошаговый визард, свёрнуто ли меню. Любые данные, которые в итоге приходят с backend (список учеников, профиль пользователя, тарифы) — не должны попадать в Redux, для них есть TanStack Query (см. выше). Если возникает соблазн положить в Redux данные с сервера — это повод остановиться и использовать TanStack Query вместо этого.

### Текущее состояние инфраструктуры

Redux-инфраструктура заведена, но пока используется чисто формально — ни одного реального раздела состояния (slice) в проекте ещё нет:

```ts
// src/shared/lib/store/store.ts
export function createReduxStore(extraArgument: ThunkExtraArg) {
  return configureStore({
    reducer: {},
    middleware: (getDefaultMiddleware) =>
      getDefaultMiddleware({
        thunk: { extraArgument },
      }),
  });
}
```

`StoreProvider` (`src/shared/lib/store/store-provider.tsx`) существует, но **намеренно не подключён** в корневом `src/app/layout.tsx` — его нужно подключить, когда появится первый реальный раздел состояния, которому он нужен, а не заранее «про запас».

### Как добавить первый/новый раздел состояния (slice)

1. Создать `slice` внутри соответствующей сущности/фичи, например `src/entities/имя-сущности/model/slice/` или, если это состояние общее для всего приложения и не относится к конкретной сущности — `src/shared/lib/store/ui/`.
2. Добавить получившийся reducer в `reducer: {}` внутри `createReduxStore` (`src/shared/lib/store/store.ts`).
3. Если `StoreProvider` ещё не подключён в `src/app/layout.tsx` — подключить его там (обернуть им дерево компонентов, аналогично тому, как уже подключены `QueryProvider` и `AppMantineProvider`).
4. Использовать типизированные хуки `useAppDispatch`/`useAppSelector` (`src/shared/lib/store/hooks.ts`) для чтения и изменения состояния — не «сырые» `useDispatch`/`useSelector` из `react-redux`, чтобы сохранялась типизация.

Готовый общий доступ к axios-клиенту `$api` из thunk-логики уже настроен через `extraArgument` (`ThunkExtraArg`, `src/shared/lib/store/types.ts`) — если понадобится сходить в API из Redux-логики (что должно быть редкой ситуацией — обычно для этого используется TanStack Query), он доступен как третий аргумент в thunk-функциях.

## Формы

Для форм в проекте используется связка react-hook-form (управление состоянием формы и обработка отправки) + zod (описание правил валидации данных). Готовых примеров форм в коде пока нет — они появятся вместе с первыми реальными страницами входа/регистрации, но ожидаемый паттерн такой:

1. Схема валидации описывается через `zod` — какие поля обязательны, какого формата, какой длины и т.п.
2. Схема подключается к `react-hook-form` через резолвер из пакета `@hookform/resolvers` (уже есть в зависимостях).
3. Сама форма — обычный `<form>` с полями Mantine (`TextInput`, `PasswordInput` и т.п.), подключёнными к `react-hook-form` через `register`/`Controller`.

Так решение о валидности данных формы описано в одном месте (схема), не разбросано по условиям внутри JSX, и совпадает и на клиенте (мгновенная проверка перед отправкой), и потенциально может переиспользоваться для проверки данных, приходящих с сервера.

## Группы маршрутов (разделы приложения)

Папки вида `(имя)` внутри `src/app/` — это группы маршрутов Next.js: способ логически сгруппировать страницы (например, дать им общий `layout.tsx`), при этом название группы не попадает в URL страницы. Так, страница `src/app/(guest)/page.tsx` открывается по адресу `/`, а не `/(guest)/`.

В проекте запланированы четыре такие группы:

| Группа | Для чего | Статус |
|---|---|---|
| `(guest)` | Публичные страницы: главная, демо-квизы, страницы входа/регистрации, юридическая информация | Есть, реализована главная страница |
| `(guest-child)` | Публичные страницы, ориентированные на детей, не требующие входа | Ещё не создана |
| `(sponsor)` | Личный кабинет Спонсора (родителя) | Ещё не создана |
| `(child)` | Личный кабинет Студента (ребёнка) | Ещё не создана |

В дальнейшем появится файл `middleware.ts`, который будет проверять, авторизован ли пользователь и какая у него роль, и автоматически перенаправлять его в нужный раздел (например, неавторизованного пользователя, который пытается открыть личный кабинет, — на страницу входа). Пока такого файла в проекте нет — это часть ещё не реализованной работы.

## Тестирование

### Модульные и компонентные тесты (Vitest)

Тестовый файл лежит рядом с тестируемым кодом, с суффиксом `.test.ts`/`.test.tsx`. Настройка — `vitest.config.ts` (окружение `jsdom`, то есть тесты выполняются в имитации браузера, без реального браузера) и `vitest.setup.ts` (общие настройки для всех тестов — например, полифилл `window.matchMedia`, которого нет в `jsdom`, но без которого не заработают некоторые хуки Mantine).

Для рендера компонента, который использует Mantine (то есть почти любого), нужно оборачивать его в тот же провайдер темы, что и в реальном приложении — для этого есть готовая утилита `renderWithProviders` (`src/shared/lib/test/render-with-providers.tsx`) вместо обычного `render` из Testing Library.

Пример реального теста (`src/widgets/Header/header.test.tsx`, сокращённо):

```tsx
import { screen } from '@testing-library/react';
import { describe, expect, it } from 'vitest';

import { renderWithProviders } from '@shared/lib/test';

import { Header } from './header';

describe('Header', () => {
  it('рендерит десктопные кнопки «Войти» и «Регистрация»', () => {
    renderWithProviders(<Header />);

    expect(screen.getByRole('button', { name: 'Войти', hidden: true })).toBeInTheDocument();
  });
});
```

Обратите внимание на `{ hidden: true }` в примере — это нужно, потому что `Header` рендерит и desktop-, и mobile-версию одновременно, переключая видимость через CSS-медиазапрос (см. раздел про SCSS выше), а инструмент для тестов не умеет вычислять настоящие медиазапросы, поэтому по умолчанию не находит «визуально скрытые» для него элементы.

Запуск всех тестов: `npm run test` (подробнее — в `README.md`).

### End-to-end тесты (Playwright)

Сквозные тесты лежат в папке `e2e/` в корне проекта (не внутри `src/`) и проверяют работу приложения по-настоящему — открывая реальный браузер и настоящий запущенный сервер разработки. Пример (`e2e/home.spec.ts`):

```ts
import { expect, test } from '@playwright/test';

test('главная страница рендерится с Header и заголовком', async ({ page }) => {
  await page.goto('/');

  await expect(page.locator('header')).toBeVisible();
  await expect(page.locator('header a[href="/"]:visible')).toBeVisible();
  await expect(page.getByRole('heading', { name: 'Hello, Next.js!' })).toBeVisible();
});
```

Здесь `:visible` в селекторе — по той же причине, что и `hidden: true` в модульном тесте выше: `Header` рендерит оба варианта верстки, и в настоящем браузере (в отличие от `jsdom`) можно точно проверить, какой из них реально виден пользователю.

Такие тесты стоит писать для целых пользовательских сценариев (открыть страницу, заполнить форму, увидеть результат), а не для проверки мелких деталей одного компонента — для этого больше подходят модульные тесты.

## Переменные окружения в коде

Все переменные окружения проекта описаны и задокументированы в `.env.example` (в корне `frontend/`) — при добавлении новой переменной обязательно дописывайте её туда с комментарием, зачем она нужна, даже если сами при разработке уже прописали значение в `.env.local`.

В коде переменные, доступные только на сервере (например, `API_URL`), читаются напрямую через `process.env.ИМЯ`. Переменные, которые должны быть доступны и в коде, выполняющемся в браузере (например, `NEXT_PUBLIC_API_URL`), обязаны начинаться с префикса `NEXT_PUBLIC_` — это требование самого Next.js, без этого префикса значение переменной не попадёт в код, собираемый для браузера. Никогда не добавляйте этот префикс к переменным, которые содержат секретные значения (пароли, ключи) — они должны оставаться доступны только на сервере.

## Частые задачи

### Добавить новую сущность (entity)

1. Создать папку `src/entities/имя-сущности/`.
2. Внутри — типы данных (обычно `model/types.ts` или похожая структура), при необходимости хуки для запросов на основе TanStack Query (публичные — через `$api`/`serverFetch`, авторизованные — через `$authApi`/`authenticatedServerFetch`, см. раздел [«Работа с данными с сервера»](#работа-с-данными-с-сервера)).
3. Экспортировать всё нужное наружу через `src/entities/имя-сущности/index.ts`.
4. Использовать сущность снаружи только через этот `index.ts` — так же, как показано на примере `Header` в разделе [«Правило публичного входа в модуль»](#правило-публичного-входа-в-модуль).

### Добавить новую страницу

1. Определить, к какой группе маршрутов она относится (см. [«Группы маршрутов»](#группы-маршрутов-разделы-приложения)) — публичная, для ребёнка без входа, кабинет Спонсора или кабинет Студента.
2. Создать файл `page.tsx` в соответствующем пути внутри `src/app/(группа)/...`. Структура папок внутри группы соответствует структуре URL.
3. Собрать страницу из уже существующих `widgets`/`features`/`entities`/`shared` — сама страница (`page.tsx`) должна оставаться простой «сборкой», а не содержать в себе логику или крупную вёрстку напрямую.
4. Если странице нужны данные с сервера сразу при открытии — использовать паттерн prefetch + hydration (см. [«Работа с данными с сервера»](#паттерн-prefetch--hydration)), а не ждать загрузки уже в браузере.

### Сделать новый запрос к API

1. Определить: нужна ли авторизация пользователя, и откуда выполняется код — из браузера (клиентский компонент, `'use client'`) или на сервере (Server Component).
2. Выбрать один из четырёх способов по таблице в разделе [«Как выполнять запросы»](#как-выполнять-запросы-четыре-варианта) — `$api`, `$authApi`, `serverFetch`, `authenticatedServerFetch`.
3. Обернуть запрос в хук TanStack Query (`useQuery` для чтения данных, `useMutation` для изменения) — не вызывать API-клиент напрямую внутри компонента без TanStack Query, иначе теряются кэширование, повторные попытки при ошибке и другие возможности, которые библиотека даёт «из коробки».
4. Типы данных, которые возвращает запрос, должны жить рядом с сущностью, к которой относятся (`src/entities/имя-сущности/`), а не быть описаны заново в каждом месте, где используются.
